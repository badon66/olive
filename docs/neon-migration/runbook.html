Olive · Supabase → Neon

Cutover Runbook

Seventeen steps, in order, from where things stand now to Olive running entirely on Neon with the Supabase project switched off. Order matters — several steps leave the app in a broken-looking state that the next one fixes.

Stage 1 Database & app Code written · steps 1–9
Stage 2 The five functions Needs code · steps 10–12
Stage 3 Scheduled jobs Needs code · step 13
Stage 4 Cutover After 1–3 · steps 14–17
Read this first

Stage 1 is written and its code compiles with 210 passing tests, but it has never run against a real Neon database — you are its first test. Stages 2 and 3 are not written yet: five Deno functions and two cron jobs still have to be ported. Until they are, the Supabase project has to stay switched on, and the free project slot the order manager needs is not released.

So Stage 1 is worth doing now on its own merits — it's also the test of whether Neon's beta Data API is good enough to continue. If it isn't, you stop at step 5 having lost nothing.

Stage 1 · The database and the app

Ready now
01

Push the branch first

Seven commits exist only on your machine. Push before you change anything else, so there's something to go back to. 

cd C:\Apps\Olive
git push -u origin neon-migration

Don't merge to main yet. Nothing here has run against a live database.

02

Install the new dependency

@neondatabase/neon-js was added to package.json, so your node_modules is out of date.

npm install
03

Install the CLI, then create the project

The neon command doesn't exist on your machine yet — that's why the terminal doesn't know the word. Install it, then open a new terminal: Windows won't put a newly installed command on the PATH of a window that's already open. 

npm i -g neon
# close this terminal, open a new one, then:
neon --version   # should print 3.6.0 or later

Now log in and create the project. The region id is aws-us-east-2 — with the aws- prefix, which the CLI requires.

neon auth
neon projects create --name olive --region-id aws-us-east-2 --set-context
neon link
Why us-east-2

Neon Functions, Object Storage and the AI Gateway are in public beta and exist only in that region. Stage 2 wants Neon Functions for your Edge Functions — they run next to the database and can stay alive for hours, which suits the assistant calling Anthropic. A project cannot change region later, so picking anywhere else closes that door permanently.

Correction

This step previously said npx neon@latest init --agent. That was my error: --agent is a machine-readable mode meant for an AI assistant driving the CLI, not a person at a prompt, and it doesn't reliably install anything. The commands above are the plain human path.

04

Provision auth and the Data API

neon.ts in the project root already declares both. This reads it, creates what's missing, and writes the matching variables into .env.local. 

neon config plan   # see what it would do — read this
neon deploy        # do it, and pull the env into .env.local

If neon still isn't recognised here, the new terminal from step 3 is the fix — or prefix every command with npx neon@latest and skip the global install entirely.

Then open .env.local and set VITE_NEON_DATABASE_URL to your project's HTTPS endpoint — it looks like https://ep-something-123456.us-east-2.aws.neon.tech/neondb, not the postgres:// string. Vite only exposes variables beginning VITE_ to the browser, which is why it needs its own line.

05

Apply the schema

Run docs/neon-migration/01-schema.sql against the new database. It rebuilds all 9 tables, 6 enum types and every index, and recreates the 9 row-level security policies against Neon's auth.user_id().

Then test that RLS is actually doing its job — an unauthenticated read must return nothing:

curl "https://<your-data-api-host>/rest/v1/tasks?select=id"
Stop condition

If that returns rows, stop and tell me. Olive is a browser app — everything it ships is public, and row-level security is the only thing between an anonymous visitor and every task, job and note you have. If the beta Data API isn't enforcing it, the whole approach changes and we go no further.

06

Copy the data across

119 rows, about 27 kB. pg_dump is the reliable route because it handles the enums, arrays and jsonb correctly — full commands are in docs/neon-migration/02-copy-data.md. 

pg_dump "<supabase-connection-string>" --data-only --schema=public \
  --no-owner --no-privileges --disable-triggers -f olive-data.sql

psql "<neon-connection-string>" -f olive-data.sql

No pg_dump on Windows? Neon's dashboard has an Import Data flow that takes the Supabase connection string and does both halves.

Don't paste these anywhere

Both connection strings are passwords. They go in your terminal, nowhere else.

08

Sign in, then remap your user id

Start the app and sign in once against Neon Auth. This creates your new account and gives you a new user id. 

npm run dev
Expected, not broken

You will be signed in and see nothing at all — no tasks, no jobs. Every row still carries your old Supabase id, and the RLS policies compare against the new one. That's the next step.

Take the new user id and run the nine UPDATE statements in docs/neon-migration/02-copy-data.md. Run them as the database owner, not through the Data API — RLS would otherwise hide the very rows you're updating.

09

Hard-refresh and check it over

Olive is a PWA, so a normal reload can serve you the old bundle from the service worker. Hard-refresh, or unregister the worker in DevTools → Application.

Worth clicking through: your tasks and categories are there, a task can be checked off, a weekly-task cube toggles, the dashboard's per-category panels are populated.

Still broken at this point

The assistant, the daily brief and the schedule-setup popup will fail with "Missing VITE_FUNCTIONS_URL". That's deliberate — a named error rather than a silent failure. They come back in Stage 2.

Stage 2 · The five functions

Code not written
10

Port the functions to Neon Functions

assistant (256 lines), schedule-setup (117), reminder-tick (68), daily-brief (60), carry-forward (20), plus 449 lines of shared code. Deno today.

Two real changes beyond the move: they must verify the Neon JWT against Neon's JWKS instead of Supabase's, and since they run server-side they can use a direct Postgres connection rather than the Data API — simpler, and not beta.

Tell me when Stage 1 works and I'll write these. I'd rather not stack more untested code on top before you've confirmed the foundation.

11

Move the secrets

anthropic_api_key, cron_secret and project_url live in Supabase Vault today, read through service-role RPCs. They move to the function host's own secret storage.

Never

None of these ever gets a VITE_ prefix. Anything so prefixed is compiled into the public bundle — your Anthropic key would be readable by anyone who opens devtools.

12

Point the app at them

One line, in .env.local and in Vercel. No trailing slash. This is the only thing that changes if the functions ever move host again. 

VITE_FUNCTIONS_URL=https://<where-the-functions-live>

The assistant, brief and schedule setup should all come back to life.

Stage 3 · The two scheduled jobs

Code not written
13

Replace pg_cron

Two jobs run in Postgres today via pg_cron and pg_net: the daily brief and carry-forward. Neon has neither extension, so they become scheduled calls from whatever hosts the functions.

The part that bites

Cron runs in UTC; Olive's scheduling is America/Edmonton, and the conversion shifts with daylight saving. Olive's own rules also draw two deliberately different rollover boundaries — the schedule page flips at 1:30 AM, but a Night period stays attributed to the day it started on until 5:00 AM. They're supposed to disagree. Get this wrong and briefs generate for the wrong day.

Stage 4 · Cutover

After 1–3
14

Set the same variables in Vercel

Settings → Environment Variables. Local .env.local is never uploaded.

VITE_NEON_DATABASE_URLthe project HTTPS endpoint

Then remove the two old VITE_SUPABASE_* variables — they're dead, and leaving them invites confusion later.

15

Merge and deploy

git checkout main
git merge neon-migration
git push

Vercel builds from main. Open the deployed app, hard-refresh, sign in, check it end to end.

16

Live on it for a few days

Use Olive normally. Watch for the things a first run wouldn't show: does the daily brief appear at the right time, do reminders fire, does carry-forward roll tasks over overnight. Leave Supabase running the whole time.

17

Pause the Supabase project

Pause, not delete. Pausing releases the free project slot just as well, and it's reversible — the data stays there. Delete it in a month if you want, or never.

This is the finish line

The moment that project pauses, the slot frees and the Powerplay order manager can be deployed — which is the reason any of this happened.

If it goes wrong

↩

Getting back to a working Olive

Nothing in Stages 1–3 touches Supabase. It stays live and intact the entire time, which means the rollback is just switching the app back: 

git checkout main   # the Supabase version, untouched
npm install
npm run dev

If you'd already deployed, restore the two VITE_SUPABASE_* variables in Vercel and redeploy from main. Your data never left Supabase — it was copied, not moved.

There's also docs/neon-migration/00-backup-core-data.sql, holding the 72 rows you'd have to retype by hand. It excludes daily_briefs, which regenerate themselves.

Worth knowing

·

Things that will confuse you otherwise

  • The stack is beta. @neondatabase/neon-js is 0.7.0-beta; the Data API, Functions and Object Storage are all public beta. For an app you open daily that's a real risk, not a footnote.
  • Your 46 database calls didn't change. Neon's Data API speaks PostgREST, the same protocol Supabase does.
  • Nor did the login. SupabaseAuthAdapter() presents Neon Auth through a Supabase-shaped API. It's a migration aid, not Neon's native one — switching to Better Auth later touches six places.
  • @supabase/supabase-js is still installed, for one TypeScript type. Not a leftover.
  • One env var replaced two. Neon derives both endpoints from the base URL and manages the JWT, so no key ships in the bundle at all.
  • Migration files stay in supabase/migrations/. The folder name is history; apply new ones to Neon.

Everything referenced here is in C:\Apps\Olive\docs\neon-migration\, and the build log with the same detail is in docs/PROGRESS.md. Stage 1 is the one that answers the real question — whether the beta Data API holds up. Get through step 5 and the rest is mechanical.
