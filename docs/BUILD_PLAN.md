# Build Plan — Olive v1

Phased spec. Each phase ends with a working, usable app. HARD GATE between phases: finish the phase, then stop and wait for the user to test the "Done when" condition and explicitly say to continue. Never begin the next phase without that approval. Phases marked **BLOCKED** have open questions (bottom of file) — do not build them until answered.

## Phase 2 — Weekly tasks + reminders (Journal REMOVED — see note below)

(Renamed from "Habits" — recurrence is more flexible than a simple streak. Naming may change again later; cheap to rename, not structural.)

- Tables: `weekly_tasks` (id, name, time_section nullable, recurrence_mode enum: `count` or `fixed_days`, target_per_week int 1-7 nullable — used when mode is `count`, scheduled_days int[] nullable — 0=Monday..6=Sunday, used when mode is `fixed_days`, task_size enum: small/medium/large, priority int 1-3, paused boolean default false, created_at), `weekly_task_checkins` (id, weekly_task_id, date, status enum: `planned`, `completed`, or `skipped` — skipped means that one day's occurrence was deliberately not done, without affecting the recurring pattern or counting as incomplete, duration_minutes nullable — kept as an editable field, no longer prompted for on check-off), `reminders` (id, name, message nullable text, recurrence_type enum: one_time/interval/daily/weekly/monthly, fire_at timestamptz nullable — for one_time, interval_minutes nullable — for interval-repeating e.g. every 30 min, days_of_week int[] nullable — for weekly, day_of_month int nullable — for monthly, time_of_day time nullable — for daily/weekly/monthly, sound_id nullable text — references a small built-in default set for now, structured so custom user-provided sounds can drop in later, volume numeric default 0.7 (0-1 range, adjustable per reminder), max_repeats int default 10 — how many times to re-alert if not dismissed, repeat_interval_seconds int default 20 — how long between re-alerts, active boolean default true, created_at).
- **Creating one asks which mode fits:** a set number of times with any day working ("4 times a week"), or specific fixed days ("Monday, Wednesday, Friday"). "Every day" = `fixed_days` with all 7 selected.
- Weekly task display: **7 cubes, Monday first through Sunday last, each cube's state fully independent of the others.** Stays a fixed Monday-through-Sunday calendar week — no rolling window. **Row layout: task name on the left, the 7 cubes on the right — a single horizontal row, not stacked with the name above and note below.** Cubes stay the same (larger) size as the current build, but must be genuinely square, not stretched into rectangles — and each still labeled with its actual date (e.g. "MON 7/21"). More space-efficient than the stacked version. A header shows the week's date range (e.g. "Week of July 21–27") **plus a summary count: how many total scheduled-day slots exist this week across all weekly tasks, and how many are still unscheduled** — a total at-a-glance, not just the per-task progress notes. Three states: empty (not scheduled that day), light green (`planned`), full/dark green (`completed`). A cube only darkens when that specific day happens and gets checked off — other cubes stay wherever they already were (e.g. Monday can be fully dark while Wednesday and Friday are still light). **Cube clicks (pencil OFF, the default) are a two-stage cycle — supersedes the earlier single-click-completes model:** clicking an empty cube marks it `planned` (light green); clicking a light-green planned cube marks it `completed` (full green); clicking a completed cube cycles back to empty (sensible default for undoing a mis-click — flag if unwanted). One press never jumps straight to completed. **With the pencil ON, clicking a cube instead edits the pattern — for fixed-days tasks, toggles that day in/out of `scheduled_days`** — unchanged from before.
- **NEW: pause a weekly task indefinitely.** A `paused` boolean on `weekly_tasks`. When paused, the task stops appearing anywhere it would normally show up — no occurrences in Today's Schedule on any day, nothing in Active Tasks, no entry in the "Unplanned Weekly Tasks" nudge, and it doesn't count toward the week's scheduled/unscheduled summary totals. **It stays visible on the Weekly Tasks tab itself, clearly marked as paused** (dimmed, with a "Paused" label), so it's easy to find and unpause — this is a pause, not an archive, and definitely not a delete. The recurrence pattern (`scheduled_days`, `target_per_week`) is untouched, so unpausing resumes exactly as before. Distinct from "Skip today" (one occurrence, one day) — pause is indefinite until manually reversed. Toggle it from the task's edit modal and/or a control on its row.
- **Today's Schedule has a small area with two distinct buttons, not a general "incomplete task" reminder mixed together:**
  - **"Unplanned Weekly Tasks"** — count-mode weekly tasks that still need days planned this week (the existing nudge, just reframed as its own explicit button, not passive text). Disappears once fully planned. Resets each Monday.
  - **"Carryover Tasks"** — one-off regular tasks that weren't completed and had `auto_carry_forward` checked, so they surface here. **Purely manual — nothing auto-moves.** The task sits in this dropdown, still on its original overdue date, until the user drags it onto a specific day/section (or clicks it to edit and set a new due date, same as any task) — at that point it's removed from the dropdown. Stays there indefinitely until manually resolved. This is NOT a general "you didn't finish this" reminder system — only tasks that explicitly opted into carrying forward land here.
  - These are two separate, clearly distinct things — don't conflate weekly-task planning with one-off task carryover.
- **How cubes get planned, per mode:**
  - `fixed_days`: scheduled weekdays light up automatically at the start of each week, no dragging needed — the pattern is already known (e.g. "gym, Mon/Wed/Fri" lights Monday/Wednesday/Friday every week on its own).
  - `count`: no fixed pattern, so planning is manual — dragging the task onto a specific day block creates a `planned` checkin for that date, lighting just that cube. Drag onto several days across the week to plan multiple at once.
  - Either way, checking it off on the actual day updates only that day's row to `completed`.
- **Progress note shows the full breakdown, not just a leftover count** — target, planned, completed, and however many still need planning, e.g. *"Target: 3x/week · Planned: 1 · Completed: 1 · 1 more to plan."* Numbers must always be internally consistent (planned + completed + remaining-to-plan = target).
- **Shows up in the actual daily schedule, not just its own tab — and this must work for ANY day being viewed: past days, today, AND future days.** Explicitly including navigating BACKWARD (previous day, two days ago) — a weekly task scheduled for that past weekday must still show there, with whatever its recorded status was (completed/planned/skipped). A task repeating every single day (all 7 days in `scheduled_days`) shows on literally every day viewed, in every direction. The correct model: whenever a day's schedule is rendered — past day, today, future day via day-nav, or an Upcoming Days block — treat a matching weekly task exactly like a regular task belonging to that day, not as a separate "weekly tasks" thing that only special-cases today. `fixed_days` tasks appear on every day in their `scheduled_days`, in their `time_section`, rendered inline alongside regular tasks. `count`-mode tasks appear on any day the week's target isn't met yet (today or future days within that week), and stop appearing once reached. Same rendering path as a normal task — not a bolted-on separate lookup that only fires for "today."
- **REMOVED: the post-confirm note/detail popup.** Checking off a weekly task is now instant and final — no popup asking for a note or duration afterward. `duration_minutes` still exists as a field, editable via the normal edit modal if wanted, but nothing prompts for it automatically anymore. *(Retrofit: this was already built, per the earlier optimistic-UI-updates work — removing the popup makes check-off match that instant-feedback expectation even better.)*
- **REMOVED: Journal.** This was already built and committed as part of Phase 2 — this is a real removal of existing code and its `journal_entries` table, not just an unbuilt spec change. Delete the feature, its route/tab, and its dashboard panel; drop the table in a migration rather than leaving it orphaned.
- **NEW: Reminders.** A dedicated sidebar tab plus a compact Dashboard mini-panel (see layout above). Covers every recurrence shape: one-time (a specific date/time, or a relative duration like "in 30 minutes"), a fixed repeating interval (e.g. every 30 minutes), daily, weekly (specific day(s)), monthly (specific day of month). Created by voice/text same as everything else, going through the same preview-before-send pattern for voice input.
- **Dashboard mini-panel: bigger and richer per reminder, not a bare name** — each entry shows its recurrence pattern at a glance (e.g. "every 30 min," "daily at 9:00 AM"). Clicking a reminder opens the same edit-modal pattern used everywhere else — no separate "edit button" needed first, consistent with the rest of the app.
- **A global "Reminders Active" toggle at the top of the Reminders tab** — a single master switch for the whole feature, separate from each individual reminder's own `active` flag. Clicking it enables/disables ALL reminders at once (when off, nothing fires, regardless of individual reminder settings). Shows current state clearly (on/off), not just a bare unlabeled toggle. Store as a simple single-value setting — a `reminders_globally_enabled` boolean, doesn't need its own table.
- **Active/counting-down reminders show a live animated countdown ring** — a circular clock-style indicator that visibly ticks down in real time, the ring depleting smoothly as the remaining time shrinks, not a static number or a bar that only updates on refresh. It should read as genuinely alive/ticking. Animate via `transform`/`opacity` only (per CLAUDE.md's performance conventions) — an SVG circle with an animated `stroke-dashoffset` is the standard approach and stays GPU-friendly.
- **When a reminder fires, it repeats until explicitly dismissed in the app** — not a one-shot alert. A pop-up stays associated with that firing; if not turned off, it re-alerts again after a set interval, up to a configurable number of attempts (default 10, spaced 20 seconds apart, both adjustable per reminder). **If there's still no response after exhausting all attempts, it stops and goes quiet until the next scheduled occurrence** (for recurring reminders) or just stops entirely (for one-time ones) — it doesn't persist as an unresolved notification once it's given up, correcting an earlier assumption. Track this with a `reminder_fires` table (id, reminder_id, fired_at, dismissed boolean default false, repeat_count int default 0) — separate from the `reminders` definition table, since this is about individual firing instances, not the recurring schedule itself.
- **Notification sound is selectable per reminder** (or a sensible global default) — **the actual sound files live in `public/sounds/`: `Double_Ding.mp3`, `Cartoon_Chime.mp3`, `Airplane_Chime.mp3`, `Service_Bell.mp3`.** Wire these four as the selectable options, with a preview/play button in the picker so a sound can be heard before choosing it. Keep `sound_id` generic enough that more files dropped into that folder can be added without a schema change. **Plus a volume adjustment per reminder** (a simple slider, 0-1 range), applied when the sound actually plays.

Must never render hidden behind another panel — this was seen overlapping the Alberta Premium Coatings section live in the app despite Phase 2 not officially having started; verify it's actually resolved, don't assume the existing spec line already caught it.

**Done when:** the 7-cube week resets correctly on Monday with each cube's planned/completed state independent and accurate for both recurrence modes; the progress note's numbers always add up; every reminder recurrence type (one-time, interval, daily, weekly, monthly) can be created and correctly fires on schedule when the app is open; Journal is fully removed, not just hidden.

## Known UI bugs — real diagnosis required, not another blind re-attempt

- **Flexible-window task date display glitches/flickers between two adjacent numbers** (e.g. rapidly alternating "Sept 6"/"Sept 7" instead of a stable value). Two likely causes to check in order: (1) a timezone off-by-one — a date stored as UTC rendering differently across re-renders depending on local-time conversion, the classic cause of dates flickering between adjacent days; (2) two different code paths computing the display date differently (e.g. one using `window_start`, another using the placed date) and fighting across re-renders. Diagnose which it actually is before fixing, and make the display stable — either the placed day or the full range ("Sept 6–12"), never an alternating value.

- **The task edit modal's background is too transparent** — it blends into the page behind it instead of standing out clearly. Increase backdrop opacity/blur so the modal reads as clearly on top of the page, not mashed into it.- **Job task-stat counts (upcoming/active/overdue) always show zero, even when real tasks exist for that job.** Diagnose, don't just re-render: check whether tasks created for a job are actually being saved with `job_id` set at all — if the job-scoped "+" add flow isn't correctly attaching `job_id` to the new task, the stat query would correctly find nothing, and the bug is in task creation, not in the counting logic. Verify directly against the database: pick a job with tasks you created for it, query its tasks by `job_id`, and confirm whether rows come back.- **Serious: completing an overdue task deletes it entirely instead of marking it complete.** Checking off an overdue task on Today's Schedule currently removes it from existence, not just from the active view. A completed task must always persist in the database with `status = completed` (or equivalent) — it should never be deleted on completion, ever, regardless of whether it was overdue. This is a data-integrity bug, not a display bug — check whether the completion handler is accidentally calling a delete instead of an update, and confirm completed tasks actually still exist in the database afterward, not just that they disappear from the screen (disappearing from the screen is correct; disappearing from existence is the bug).- **Active Jobs "add task" popup — reported fixed once already, confirmed still broken.** It renders inline inside the job's card instead of as a proper overlay. ## Phase 6 — Finance agent (reads from YNAB, read-only)

**The division of responsibility, stated explicitly so it's never re-litigated:** YNAB is the system of record for the money itself — categorization, budgeting, payee management, all of it. Olive doesn't compete with that or rebuild it. Olive's job is to be the thing that already knows everything ELSE — your schedule, your jobs, your income pace, your tasks — and merge YNAB's data into that bigger picture. The value Olive adds is entirely in the cross-referencing (spend vs. income pace, a nudge landing in Today's Schedule instead of buried in a separate app) — never in re-doing what YNAB already does well. Any future work on this phase should be read with that framing, not as "build a finance feature" in isolation.

Switched from Plaid to reading directly from the user's own YNAB budget — YNAB already handles bank linking, categorization, and payee sorting, so Olive doesn't rebuild any of that.

- **YNAB Personal Access Token** (self-service — user generates it in YNAB's own Account Settings → Developer Settings, no approval process needed), stored server-side as a secret, same pattern as every other key.
- Daily sync into `finance_snapshot` tables (accounts, balances, transactions) pulled straight from the YNAB API — **transactions arrive already categorized and payee-matched by YNAB itself.** No Olive-side auto-categorization or merchant-memory build needed; that's YNAB's job now, not ours.
- **YNAB stays read-only from Olive, same as the Google Sheet** — Olive never writes a category correction back to YNAB. If a transaction is uncategorized in YNAB, Olive surfaces a reminder to go categorize it there, exactly like the Sheet's "reminder, not auto-write" rule. *(Flagging this as the default for consistency with the rest of the app — say so if you actually want Olive to write categories back to YNAB instead.)*
- **Uncategorized-in-YNAB transactions surface as a nudge in the Today's Schedule nudge area** (same pattern as Unplanned Weekly Tasks / Carryover Tasks) — a reminder to go categorize them in YNAB, not just something buried in the Finance tab.
- Recurring-charge detection, built on top of the synced transaction history — upcoming known charges appear in the brief N days ahead. **Also detect genuinely NEW recurring charges** (a pattern that didn't exist before starts repeating) — flagged distinctly, the "wait, when did I sign up for that" catch.
- **Dashboard mini-panel stays simple** (per the existing Dashboard/full-tab split pattern used elsewhere): balance, today's spend, pace vs goal only — no transaction list here.
- **Full Finance sidebar tab gets the real depth:**
  - **Recent Transactions** — shown with YNAB's own category and payee already attached.
  - Category breakdown for the period (where the money's actually going), using YNAB's categories as-is.
  - **Spend-vs-income-pace cross-reference** — combines the income pace tracker (Phase 7) with actual spending into one insight, something neither shows alone.
- Brief shows a daily money section: current balance + total spent today (confirmed definition).
- Staleness is first-class: if the YNAB token/connection breaks, show "data from <date> — tap to re-link," never silently-wrong numbers.

**Done when:** real balance + recent transactions render with YNAB's own categories intact; uncategorized-in-YNAB items nudge correctly in Today's Schedule; a known subscription is flagged before it hits, and a genuinely new one is flagged distinctly; a broken connection shows the stale-data state.
